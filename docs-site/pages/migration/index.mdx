# Migration

Moosewave migrations use a source adapter, a canonical read model, a dry-run verifier, and tenant-scoped destination writers. The runtime capability response at `GET /api/v1/migrations/sources` is authoritative for which sources and resource families are available in a deployment.

## Common lifecycle

1. **Connect** using the authentication method advertised by the source capability.
2. **Discover** source inventory and warnings. Audience-scoped sources can require explicit selection.
3. **Dry-run** read and translate the selected scope without writing destination records.
4. **Review** the verification report, warnings, completeness states, and manual rebuild work.
5. **Commit** the same source job and scope while streaming per-resource progress.
6. **Verify** destination behavior through normal Moosewave subscriber, segment, template, archive, and automation paths.
7. **Roll back**, when eligible, from the migration's write ledger before `rollback_until`.

Canonical statuses are `pending`, `authenticating`, `discovering`, `dry_run`, `awaiting_confirmation`, `importing`, `rolling_back`, `completed`, `failed`, and `rolled_back`.

Progress counters cover subscribers, segments, automations, paid subscriptions, campaign archive, templates, and source archive.

## Canonical subscriber shape

```json
{
  "email": "member@example.com",
  "status": "enabled | disabled | blocklisted | unconfirmed",
  "consent_timestamp": "iso8601 or null",
  "consent_source": "double_optin | single_optin | import | api | unknown",
  "custom_fields": { "first_name": "Ada" },
  "tags": ["audience:main"],
  "source_id": "provider-id",
  "source_platform": "mailchimp"
}
```

Segments use a portable query AST, but a source predicate is executable only when its referenced data exists on imported destination subscribers and verification succeeds. Automations use explicit triggers, nodes, edges, and destination resource references; imports remain paused until reviewed.

## Verification and rollback

The [verification report](/migration/verification-report) exposes observed counts, consent provenance, duplicate merges, translation warnings, rebuild work, resource completeness, and the data-loss estimate. It does not include a signed payload hash or an automatic business-equivalence guarantee.

The [rollback contract](/migration/rollback) uses the migration write ledger. It removes records created by the job and restores before-images for pre-existing records updated by the job. It does not alter the source platform, undo sends, or change external billing/DNS state.
