# beehiiv Migration Source

Status: Migration-only API v2 adapter; live certification pending.

beehiiv also has a separate `beehiiv` native-foundation row for provider lifecycle and run evidence. This `beehiiv-migration` tile remains the publication-scoped migration surface.

## Authentication and Scope

The adapter always validates the API key against `/workspaces/identify`, lists the publications available to that workspace, and binds the session to one workspace/publication identity. A single available publication can be selected automatically. A workspace with multiple publications requires an explicit `account_id`/`publication_id`; no publication chooser is implemented yet. A supplied publication must belong to the authenticated workspace.

Beehiiv documents one 180-request-per-minute organization quota. Moosewave uses a conservative bounded 170-request bucket per authenticated workspace. The unauthenticated identify call first passes through one shared admission bucket; as soon as Beehiiv reveals the workspace, that same identify request is also charged to the workspace bucket before publication discovery continues. Thus credential bootstrap cannot create a second allowance beside the organization budget. Workspace limiter entries are opaque-hashed, idle-expiring, and hard-capped in memory.

The key must include `identify:read`, `publications:read`, `subscriptions:read`, `newsletter_lists:read`, `segments:read`, `condition_sets:read`, `automations:read`, `posts:read`, and `custom_fields:read`. These cover workspace/publication binding, subscriptions, newsletter-list definitions/history, segments, dynamic-content condition sets, automation definitions/emails/journeys, posts, and custom-field definitions. They are discovery/runtime prerequisites, not optional archive extras: a denied, missing, or incomplete response fails the dry run instead of becoming a waivable warning. Tier, referral, poll, and post-template access may still vary by plan or permission and is represented by sanitized source-archive review warnings.

## Runtime Coverage

- Cursor-paginated subscribers with source status and stable source IDs.
- Custom-field values plus source-preserved field definitions (`id`, `display`, `kind`, creation time, and list options), expanded newsletter-list metadata, and premium-membership metadata. Because final-delta writes are authoritative, each subscription must contain `subscription_tier`, non-null `subscription_premium_tier_names`, and non-null `custom_fields`, `newsletter_list_ids`, `tags`, and `subscription_premium_tiers` arrays; explicit empty arrays remain valid, while an omitted/null array, nameless/unkinded custom field, duplicate item, or invalid tag fails closed before a destination write. Every custom-field item must include an explicit `value`: explicit JSON `null` is preserved as an intentional source-side removal, while an omitted value or a non-null value that does not match its documented `string`, `integer`, `boolean`, `date`, `datetime`, `list`, or `double` kind fails closed. Source field names in Moosewave-reserved namespaces are injectively escaped with an original-to-destination ledger instead of being reinterpreted as control metadata.
- Newsletter-list memberships as `beehiiv:newsletter-list:{id}` tags and tag-backed segments. Raw Beehiiv tags that collide with this synthetic namespace are injectively escaped and ledgered so a source label cannot forge list/segment membership.
- Newsletter-list definitions and cursor-paginated active/pending/inactive/paused subscription history as read-only source evidence. One durable completion manifest per discovery-bound list proves that its history endpoint was traversed even when it returned zero records.
- Every accessible segment's stable metadata/calculation state as source evidence. Completed, fully readable memberships become frozen `beehiiv:segment:{id}` tag-backed snapshots. API v2 does not expose portable predicates, so dynamic behavior requires rebuild. The final traversal proves that every snapshotted member ID exists and that applied per-segment tag counts equal the snapshot total. The worker also enforces a 250,000-link account-wide evidence ceiling; over-budget segments fail closed as rebuild items instead of producing partial targeting.
- Active dynamic-content condition-set identity/lifecycle metadata plus a durable `condition_sets:read` cursor-completion manifest, including an empty inventory. Saved condition-set predicates are not exposed, so they share the post-delta dynamic-audience rebuild/retirement review.
- Automation metadata, trigger labels, email metadata/statistics, and per-subscriber journey state as `rebuild_review` source definitions. Requested automation statistics must contain a documented `journeys` and/or aggregate `email` object: journey `running`, `completed`, and `total` counts and the core aggregate-email counters are validated as non-negative integers, while optional rates must be finite numbers. Every automation email must likewise contain the documented core engagement counters; absent, unknown-only, incomplete, or malformed analytics fail closed rather than producing a misleading complete manifest. Separate durable completion manifests per discovery-bound automation prove both email and journey inventories were traversed even when empty. Journey history is offset-capped at 10,000 rows per automation (100 pages × 100); a larger history fails closed. These records have no executable graph/nodes and are never activated.
- Only past, published `email` or `both` posts as campaign archive entries. The lightweight post inventory is classified at one run-bound cutoff, then each applicable post is expanded individually with the official `expand` parameter. Requested free/premium email/web/RSS members and core email-stat counters must be present with valid shapes; optional analytics remain raw/presence-aware rather than being fabricated as zero. Draft, scheduled, web-only, and other non-campaign posts are source-preserved instead.
- Accessible publication, premium-tier, referral-milestone, poll/response, and post-template records as source archive evidence. Template bodies are not claimed when the endpoint returns metadata only.
- Cross-page archive identity verification is bounded to 1,000,000 identity-bearing rows per archive traversal. A larger inventory fails closed as unsupported instead of risking worker exhaustion or certifying a partial history.

Subscription creation time and membership do not establish portable channel-consent proof. Subscriber consent provenance remains unknown unless another reviewed source supplies it.

## Delta and Deletion Reconciliation

The adapter does not provide a live webhook or source-event bridge. Cutover requires a final full delta. Before deletion reconciliation, the completed traversal must contain exactly the discovery-bound number of unique Beehiiv subscription IDs; missing cursor metadata, cursor cycles, count drift, or duplicate identities fail closed. The commit path then compares stable IDs with the same job's active subscriber ledger and disables identities that disappeared from the source snapshot. It does not infer deletion from email alone or modify contacts owned by another source/job. If duplicate source IDs previously merged into one email and the destination-owned ID disappears, ownership is transferred only to a still-present, previously tracked ID under a locked ledger proof so status, tags, and fields remain authoritative.

Every new subscriber ledger also stores a bounded, source-specific canonical projection instead of trying to infer ownership from a merged destination after-image. Before any Listmonk request, the worker validates the same-job projection aggregate (at most 32 identities and 2 MiB); only an exact single-identity legacy ledger can be backfilled safely. If a different job for the same provider still owns the shared destination email, final-delta reconciliation verifies the tracked destination's migration fingerprint and performs an update-only rebuild from all exact active projections: retiring-only tags, custom fields, native tag joins, and list memberships are removed; shared/local state and defensible consent remain; and primary source identity/status authority transfers to the survivor. An explicit local-status baseline is carried across chained A→B→C retirements so a retired source's suppression does not become local state. A non-owner ledger, ambiguous legacy state, exceeded bound, externally changed destination, conflicting survivor value, or aggregate spanning multiple providers fails before external mutation. A survivor ledger produced by this cleanup is marked rollback-blocked because its historical before-image contains the retired targeting state; projection-aware rollback must be implemented and certified before that case can pass rollback rehearsal for self-serve release.

Every successful destination-writing Beehiiv run also stores a bounded, versioned, non-reversible source fingerprint and a new opaque import epoch on the migration job. The fingerprint covers canonical subscriber identity, email, status, fields, raw tags, newsletter-list and segment membership; segment/list definitions; automation definitions; sent-post archives; and the full source archive, including automation email/journey and non-campaign-post evidence. A credentialed shadow check retraverses those surfaces and compares per-component digests, so an edit, deletion, or replacement is detected even when every discovery count remains unchanged. Its durable result is bound to both the fingerprint digest and that exact successful-import epoch; pilot acceptance rejects evidence from an earlier delta even if replica clocks are skewed or the source content digest did not change. A missing or invalid baseline requires another final delta before cutover review.

Direct and monitored shadow checks first rotate a durable opaque attempt token on the job and persist a fail-closed attempt-start record carrying that token before any provider traversal, then persist the completed result after execution leases are released. A crash leaves either the new token with no matching result or the start record latest; provider, persistence, or lease-release errors produce `check_failed` evidence and block pilot acceptance. The provider traversal is not started when the attempt identity or start record cannot be saved. History prioritizes evidence matching the job's current attempt token, so an older ready row cannot outrank a newer sentinel because another replica's clock is ahead. Beehiiv pilot acceptance additionally uses the exact import-epoch and baseline-fingerprint binding—not wall-clock ordering—to prove that the ready result belongs to the latest successful final delta.

## Rebuild and Billing Boundaries

Premium tier and membership metadata is preserved, but the adapter does not migrate Stripe customers, products, prices, subscriptions, renewals, or tenant-bound billing ownership. `ListPaidSubs` remains unsupported.

Publication websites/themes, navigation, custom pages, capture widgets, Boosts, recommendation relationships, and ad-network configuration/history require manual inventory and rebuild. Strict pilot acceptance requires separate website/theme/capture, Boosts/recommendations, Ad Network, and source-automation retirement evidence recorded after the latest successful final delta. For automations the safe order is: inventory running source flows, pause/retire them, capture the final journey and subscriber delta snapshot, verify shadow/rollback evidence, then activate tested Moosewave rebuilds. Each provider-only review also requires its durable archive record; evidence cannot waive a missing record. Accessible referrals, polls, and post-template metadata are evidence, not activated Moosewave growth, form, or template surfaces.

This tile does not claim native beehiiv webhooks, continuous source-event polling, writeback, provider-side cleanup automation, portable consent proof, executable segment predicates, executable automations, Stripe billing continuity, or live publication certification.
